# Backend Tech Stack & Implementation Spec

Audience: AI coding agents and backend teammates.  
Scope: **backend tech stack, structure, and implementation rules only.** Business rules (valuation formula, offering lifecycle, invariants, fixtures) live in [MEGA_PLAN.md](MEGA_PLAN.md); section references below (`§N`) point there.  
Time budget: 24-hour hackathon. Prefer the simplest option that preserves settlement correctness.

Keywords **MUST**, **MUST NOT**, **SHOULD** are normative.

---

## 1. Stack (fixed — do not substitute)

| Concern | Choice | Notes |
| --- | --- | --- |
| Language | TypeScript, `strict: true` | No `any` in `lib/` |
| Runtime | Node.js 22 LTS or newer | Route handlers use the Node runtime, not Edge |
| Web + API | Next.js (App Router), route handlers in `app/api/**/route.ts` | Single app for UI + API |
| Database | Supabase Postgres | Single source of truth for money, shares, orders |
| Auth | Supabase Auth (email magic link or email/password) via `@supabase/ssr` | Session in cookies |
| DB client | `@supabase/supabase-js` + generated types | **No ORM** |
| Atomic mutations | PL/pgSQL functions called with `supabase.rpc()` | See §5 |
| Validation | `zod` | Every request body, query, and header |
| Migrations / local DB | Supabase CLI (`supabase/migrations/*.sql`, `supabase/seed.sql`) | Plain SQL only |
| Tests | `vitest` (unit + integration against local Supabase); `pgTAP` optional | §9 |
| Hosting | Vercel (app) + Supabase Cloud (DB/Auth) | |
| Package manager | `pnpm` | Pin exact versions in `package.json` |

### Explicitly banned for the MVP

Prisma, Drizzle, TypeORM, any second migration system; a separate Express/FastAPI/Nest server; microservices; Redis; message queues (BullMQ, Kafka, SQS); GraphQL; Edge runtime for mutation routes; client-side writes to any money/share table; any external HTTP call inside a settlement transaction.

## 3. Layer responsibilities

| Layer | MUST do | MUST NOT do |
| --- | --- | --- |
| Route handler (`app/api`) | Parse/validate with zod, get user from session, call one RPC or a select, map errors | Compute prices/balances that get persisted; run multiple dependent writes |
| `lib/domain`, `lib/valuation` | Pure functions, no I/O, fully unit-tested | Import Supabase or Next.js |
| SQL functions | All writes to ledger, holdings, share events, orders, quotes, offering status, grants | Trust any price/total/balance passed in from the client |
| RLS-scoped selects | All read endpoints | Use the service-role key |

Rule of thumb: **if a request changes credits, shares, quotes, or offering status, it is exactly one `rpc()` call.** Everything else may be an ordinary RLS-scoped `select`/`insert`/`update` from the route handler.

## 4. Database conventions

- Primary keys: `uuid default gen_random_uuid()`.
- Timestamps: `timestamptz default now()`; all deadline comparisons use database `now()`, never client time.
- Money: `bigint` cents. Quantities: `bigint`, `CHECK (quantity > 0)`.
- JS-safe range: app-level bounds keep every value below 2^53 (quantity ≤ 10,000,000; unit price ≤ 100,000,000 cents). Add matching `CHECK` constraints.
- Enums: Postgres `enum` types for `stage`, `entity_status`, `offering_status`, `instrument_type`, `order_status`, `evidence_status`.
- Every mutable money/share table carries `scenario_id` + `generation` (§23 isolation).
- Required unique constraints (§14): `(actor_id, operation, idempotency_key)`; `orders(quote_id)`; one primary journal per order; one issuance `share_event` per order; `holdings(owner_id, instrument_id)`; one grant per `(account, scenario_id, generation)`; partial unique index `offerings(company_id) WHERE status = 'PUBLISHED'`; `follows(user_id, company_id)`.
- Naming: tables `snake_case` plural; functions `snake_case` verbs; parameters prefixed `p_`, locals `v_`.

### Privileges (apply in `0003_rls_policies.sql`)

```sql
alter table <every_table> enable row level security;

-- Money/share tables: no direct client writes at all.
revoke insert, update, delete on journal_entries, journal_lines, ledger_accounts,
  holdings, share_events, orders, quotes, idempotency_records, outbox_events
  from anon, authenticated;
```

- Read policies: owner-only for `ledger_accounts`, `holdings`, `orders`, `quotes`; public read for published `companies`, `founder_profiles`, `offerings`; founder-only for private valuation inputs.
- Founder-editable tables (`companies`, `founder_profiles`, `company_sources`, `valuation_inputs`) allow insert/update where `owner_id = auth.uid()`.

## 5. SQL function catalog

All mutating functions follow this template:

```sql
create or replace function public.<name>(<params>)
returns jsonb
language plpgsql
security definer
set search_path = public, pg_temp
as $$
declare
  v_actor uuid := auth.uid();
begin
  if v_actor is null then
    raise exception 'UNAUTHENTICATED' using errcode = 'P0001';
  end if;
  -- ...
end;
$$;

revoke all on function public.<name>(<param types>) from public, anon;
grant execute on function public.<name>(<param types>) to authenticated;
```

**Error convention:** business errors are `raise exception '<ERROR_CODE>' using errcode = 'P0001'`. The message is exactly one code from §7. Optional detail goes in `using detail = '...'` (no private data).

| Function | Signature | Purpose |
| --- | --- | --- |
| `post_journal` | `(p_operation text, p_order_id uuid, p_lines jsonb) returns uuid` | **Internal only** (no grant to `authenticated`). Inserts entry + lines, asserts `sum = 0`, updates cached balances, asserts non-negative for every non-source account |
| `grant_demo_credits` | `() returns jsonb` | One $1,000 grant per user per scenario generation; returns balance |
| `create_quote` | `(p_offering_id uuid, p_quantity bigint) returns jsonb` | Reads published price from DB, computes total, `expires_at = least(now() + interval '60 seconds', close_at)`; returns §19 quote JSON |
| `purchase` | `(p_quote_id uuid, p_idempotency_key text, p_request_hash text) returns jsonb` | Atomic settlement (§5.1) |
| `get_purchase_by_key` | `(p_idempotency_key text) returns jsonb` | Timeout recovery; caller's own records only |
| `publish_offering` | `(p_offering_id uuid) returns jsonb` | Locks company row, validates, sets `PUBLISHED`, snapshots terms |
| `close_offering` | `(p_offering_id uuid) returns jsonb` | Locks offering row (same lock as purchase), sets `CLOSED` |
| `demo_reset` | `(p_scenario_id uuid) returns jsonb` | Controller-only; increments generation, invalidates quotes; never deletes journals |
| `demo_reconcile` | `(p_scenario_id uuid) returns jsonb` | Runs every check in §18; returns `{ ok, checks: [{ name, ok, detail }] }` |

### 5.1 `purchase` lock order (MUST follow exactly)

```text
1. pg_advisory_xact_lock(hashtextextended(v_actor::text || ':purchase:' || p_idempotency_key, 0))
2. idempotency_records lookup:
     found + same request_hash   -> return stored result
     found + different hash      -> raise IDEMPOTENCY_CONFLICT
3. select quote ... for update          (must belong to v_actor)
     quote already consumed         -> raise IDEMPOTENCY_CONFLICT (detail: existing order id)
4. select offering ... for update       (common gate for purchase AND close)
5. select ledger_accounts where id in (investor, startup)
     order by id for update             (sorted UUID order)
6. select instrument ... for update; then holding row for update (insert if absent)
7. revalidate: generation, quote unexpired (db now()), offering PUBLISHED, now() < close_at,
   price/terms unchanged, investor != founder, per-order + cumulative investor limits,
   remaining capacity >= quantity, investor available balance >= total
8. insert order (status SETTLED, settled_at = now())
9. post_journal('PURCHASE', order_id, [investor -total, startup +total])
10. insert share_event (PRIMARY_ISSUANCE); update holding qty + cost basis;
    update instruments.total_issued; update offerings.sold_units; set SOLD_OUT if sold_units = cap
11. mark quote consumed (consumed_order_id = order_id)
12. insert audit_events, outbox_events, idempotency_records(result jsonb)
13. return result jsonb { order, balanceCents, holding }
```

Any `raise` rolls back everything. MUST NOT add `exception when others` blocks that swallow errors.

## 6. API route pattern

Every route handler uses one wrapper so auth, validation, request IDs, and error mapping are uniform.

```ts
// app/api/purchases/route.ts
import { z } from "zod";
import { withHandler } from "@/lib/http/handler";
import { requireIdempotencyKey, hashRequest } from "@/lib/http/idempotency";

export const runtime = "nodejs";

const Body = z.object({ quoteId: z.string().uuid() });

export const POST = withHandler(
  { auth: true, body: Body, retrySettlement: true },
  async ({ supabase, body, req }) => {
    const key = requireIdempotencyKey(req); // throws MISSING_IDEMPOTENCY_KEY (8–128 chars)
    const { data, error } = await supabase.rpc("purchase", {
      p_quote_id: body.quoteId,
      p_idempotency_key: key,
      p_request_hash: hashRequest(body),
    });
    if (error) throw error; // mapped by withHandler
    return data;
  },
);
```

`withHandler` responsibilities:

1. Generate `requestId` (`crypto.randomUUID()`), return it as `x-request-id`.
2. Create the user-scoped client via `createServerSupabase()`; when `auth: true`, call `supabase.auth.getUser()` and throw `UNAUTHENTICATED` if absent.
3. Parse body/query with zod; failures become `INVALID_INPUT` (400) with field paths.
4. Map errors: Supabase/PostgREST error with `code === "P0001"` → `message` is the app error code; `40001`/`40P01` → retry, then `RETRYABLE_SETTLEMENT_ERROR`; anything else → 500 `INTERNAL` with no internals leaked.
5. When `retrySettlement: true`: up to 3 attempts on `40001`/`40P01`, jittered 50–200 ms, **same idempotency key**.
6. Log `{ requestId, route, userId, errorCode, durationMs }` only; never balances, financial inputs, or emails.

Response shapes:

```jsonc
// success: the RPC/domain JSON directly, HTTP 200 (201 for creates)
// error:
{ "error": { "code": "INSUFFICIENT_CREDITS", "message": "Not enough demo credits.", "requestId": "..." } }
```

## 7. Error codes → HTTP status

| Code | HTTP |
| --- | --- |
| `UNAUTHENTICATED` | 401 |
| `FORBIDDEN` | 403 |
| `NOT_FOUND` | 404 |
| `INVALID_INPUT`, `INVALID_QUANTITY`, `INVALID_VALUATION_INPUT`, `MISSING_IDEMPOTENCY_KEY` | 400 |
| `QUOTE_EXPIRED`, `ROUND_CLOSED`, `ALLOCATION_UNAVAILABLE`, `INSUFFICIENT_CREDITS`, `SELF_PURCHASE_FORBIDDEN`, `STALE_GENERATION`, `OFFERING_ALREADY_ACTIVE`, `IDEMPOTENCY_CONFLICT` | 409 |

| `RETRYABLE_SETTLEMENT_ERROR` | 503 |
| `INTERNAL` | 500 |

Keep this list in `lib/http/errors.ts` as a `const` object. SQL functions may only raise codes from it.

## 8. Supabase clients

```ts
// lib/db/server.ts: use in all route handlers
import { cookies } from "next/headers";
import { createServerClient } from "@supabase/ssr";
import type { Database } from "./types";

export async function createServerSupabase() {
  const cookieStore = await cookies();
  return createServerClient<Database>(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!,
    {
      cookies: {
        getAll: () => cookieStore.getAll(),
        setAll: (list) =>
          list.forEach(({ name, value, options }) => cookieStore.set(name, value, options)),
      },
    },
  );
}
```

- `lib/db/admin.ts` uses `SUPABASE_SERVICE_ROLE_KEY`, begins with `import "server-only"`, and is imported **only** by seed/reset scripts and integration-test setup, never by a user-facing route.
- Regenerate types after every migration: `pnpm db:types`.

## 9. Testing

| Suite | Tool | Runs against | Must cover |
| --- | --- | --- | --- |
| `tests/domain` | vitest | nothing (pure) | §26 domain cases: valuation golden cases, cents math, dilution, rounding, bounds |
| `tests/integration` | vitest | local Supabase (`supabase start`) | Every row of the §26 integration table |
| `supabase/tests` (optional) | pgTAP | local Supabase | Privilege revokes, constraint existence, reconcile on seed data |

Integration test conventions:

- Create test users with the admin client, then sign in to get **user-scoped** clients. Tests must exercise RLS and function grants, not bypass them.
- Concurrency tests use `Promise.all` over separate user clients (e.g. two buyers × 7 units on a 10-unit offering → exactly one success, one `ALLOCATION_UNAVAILABLE`).
- Every integration test ends by calling `demo_reconcile` and asserting `ok === true`.
- Each test file uses its own scenario so files can run in parallel.

## 12. Deployment

1. Create the Supabase Cloud project; `supabase link --project-ref <ref>`; `pnpm db:push`.
2. Seed the hosted DB once with `seed.sql` (SQL editor or `psql`). Never run `db reset` against the hosted project.
3. Vercel: import the repo, set the env vars from §10, deploy from `main`.
4. Supabase Auth → URL configuration: add the Vercel domain to Site URL and redirect URLs.
5. Hosted smoke test: grant → quote → purchase → refresh portfolio → founder dashboard → `/api/demo/reconcile` returns `ok: true`.
